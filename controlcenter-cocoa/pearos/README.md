# ControlCenter on pearOS

How `apps/controlcenter-cocoa` is installed and started on pearOS (the Mac frameworks it links come from the owner's Mac through `macdeps`; the binary and its sources are ours, BSD-2-Clause).

## Install layout
`/System/Library/CoreServices/ControlCenter.app` (our bundle: `Contents/MacOS/ControlCenter`, `Contents/Info.plist` with `com.apple.controlcenter`, `LSUIElement`). The Apple one is never installed on pearOS, so the path is free.

## Services (launchd job)
`pearos/com.apple.controlcenter.plist` declares the same MachServices as Apple's job (`com.apple.controlcenter.ccutil`, `.controlcentermodule`, `.show.toggles`, `.statusitems`, `com.apple.SystemBanner`, `com.apple.SystemBannerService`). The launchd of `d/darwin` takes at most 6 names per stub and 256 programs.

## Build
Today: a Mach-O built on the Mac VM (`research/cc-trace/deploy-ours.sh`, `make` here), copied to the image. Wanted: a build on FreeBSD with clang + ld64.lld and `-undefined dynamic_lookup` like `/open` (`open/build-appkit-bsd.sh`): needs headers for QuartzCore, CoreText, ImageIO, xpc, IOKit/ps, ApplicationServices that the open SDK tree (`dyld/tools/sdk`) does not have yet.

## Status of the run on the ISO test VM (2026-11-18)
Setup used (ISO test VM, `~/.pear/isotest`, ssh port 2224, cache disk on a virtio drive mounted at /System/Volumes): the thin Mac `dyld` installed at `/usr/lib/dyld` through a tmpfs + unionfs over `/usr/lib` (the ISO root is cd9660, read-only), `binmiscctl disable macho64 / machofat`, `kern.darwinator.{dyld=1,two_volumes=2,fast_sleep_ms=5}`, our `ControlCenter.app` built on the Mac VM copied to `~/cc` (chmod +x).
1. **Found and fixed (darwinator, `src/syscalls_event.c`): `getfsstat64` looped forever.** Two causes: the root of the ISO is cd9660, but the "second volume" logic only recognised ufs / zfs roots (count of the first pass one more than the entries of the second, so dyld never settled): now the root volume is the mount on `/`, whatever the file system; and the buffer of the second pass was `maxn-1` entries, which cut off the last real mounts when msdosfs mounts (EFI partition, cache disk) came before them: now there is room for them. The module was rebuilt on the lab VM from the releng/14.5 kernel sources and loaded in the ISO VM: the loop is gone.
2. **Next blocker:** `dyld: Library not loaded: /System/Library/Frameworks/Foundation.framework/Versions/C/Foundation ... (slice is not valid mach-o file)`. The ISO installs GNUstep stand-ins (ELF) at the Mac framework paths (`iso/manifest/frameworks.txt`), and the Mac dyld looks at that file instead of taking the library from the shared cache (the cache disk is there, `shared_region_check_np` is called). To do: make dyld take system libraries from the cache (the macOS 26 cache has them as "not expected on disk": check why dyld prefers the disk file, `kern.darwinator.use_cache`, the shared-region mapping of the cache from the disk's path), or keep the stand-ins out of the paths the cache provides when the Mac stack is used.
2b. **Found (same day): dyld looks for the cache in `/System/Library/dyld/` (and `/System/Cryptexes/OS/System/Library/dyld`), neither exists on the ISO** (the cache disk is at `/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld`, and darwinator does not redirect it). So the Mac dyld never saw the cache and went to the disk file (the GNUstep ELF). With a tmpfs + unionfs over `/System/Library` and a symlink `/System/Library/dyld -> /System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld` the "Library not loaded: Foundation" error is gone and the process runs on (it then waits: no launchd / window server in that VM). To do in the image: `/System/Library/dyld` (symlink, or a mount of the cache disk there) created by the overlay / rc script that sets up the Mac stack, instead of a manual unionfs. **Correction (later the same day):** the "spin" was not the app: the kernel stack of the process was `vn_fullpath_any -> vn_fullpath_dir -> vn_vptocnp -> _vn_lock_fallback`, i.e. `fsgetpath` (dyld asks for the path of a cache file) looping in the kernel on vnodes of my **unionfs** test mounts over `/usr/lib` and `/System/Library`; the process became unkillable (23 minutes of CPU, later runs queued behind it in state `DN` on the same vnode lock) and the VM had to be restarted. So: do NOT use unionfs for this; the image must provide `/usr/lib/dyld` and `/System/Library/dyld` in its own tree (the ISO build) or through nullfs/tmpfs copies. Earlier wording, superseded: the process RUNS (state RL, load 2.5 for 7 minutes, ignoring SIGTERM from `timeout`: it spins, probably in a kevent / workqueue loop while it waits for services that do not exist in that VM): to look at with `kern.darwinator.debug=2` and the real stack (launchd, wsd).
3. Then: services (launchd with the job plist here), wsd as SkyLight server, the CA render stub, as for the Dock/Finder (`d/session/pearos-desktop.sh`).

## Result of 2026-11-18 (evening): our ControlCenter RUNS on the ISO test VM
Clean setup (no unionfs): a tmpfs of 900 MB with copies of `/System/Library` (210 MB, plus a symlink `dyld -> /System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld`) and of `/usr/lib` (plus the Mac's thin `dyld`), each put over the original with **nullfs**; cache disk (virtio, msdosfs) on `/System/Volumes`; rebuilt `darwinator.ko` loaded; `kern.darwinator.{dyld=1,two_volumes=2,fast_sleep_ms=5}`; `binmiscctl disable macho64/machofat`. (The script of the run is in the notes of this session: tmpfs + `cp -a` + `mount -t nullfs`.)
Third darwinator defect found and fixed (`src/syscalls_more.c`): `fsgetpath` called `VFS_VGET` on the root mount with the file id of the caller; on the ISO the root is cd9660, whose VGET takes the number as a block offset and returns garbage vnodes, so `vn_fullpath` spun forever in the kernel (unkillable process, 23 minutes of CPU, procstat: `vn_fullpath_any -> vn_fullpath_dir -> vn_vptocnp`). It now answers ENOENT for a cd9660 root (a proper fix: look the mount up by the fsid the caller passes).
What happens now: dyld loads the app and Foundation, QuartzCore, CoreGraphics ... from the cache, `main` runs our code, `CCServices` creates the XPC connections, and the process waits in `mach_msg` (state `machmsg`) because this VM has no launchd stack; our log says `cc: window 0/1/2 not created` (no SkyLight server: the status-item windows need `wsd`). `kevent filter -17` is not implemented (logged 28 times, harmless so far).
Next: the services (the launchd of `d/darwin` with `com.apple.controlcenter.plist`, notifyd, cfprefsd, lsd ...), `wsd` + `wsbridge` as the SkyLight server, the CA render stub; then the status items and the panel should draw on wsd like the Dock does (`d/session/pearos-desktop.sh`).

## Stack on the ISO test VM (2026-11-18, later): the status items reach wsd
Built on the lab VM (`pkg install llvm21`, then `d/darwin/build.sh` and `make -C WindowServer SKYLIGHT=../SkyLight wsd`) and copied to the ISO VM (`iso-stack.sh`: wsd headless 1280x800 + our launchd with notifyd, wsbridge, the Mac's cfprefsd daemon/agent, lsd-stub, carender-stub, a svc-stub for `com.apple.PowerManagement.control`). With that stack ControlCenter stays alive and **wsd lists exactly the windows of the Mac**: `window 1 level 25 1063,0 31x30`, `window 4 level 25 1094,0 42x30`, `window 6 level 25 1136,0 144x30` (SkyLight window creation, levels and frames work through wsbridge). A crash was fixed on the way: `NSDateFormatter stringFromDate:` returns nil on pearOS (ICU data) and made `[NSAttributedString initWithString:nil]` throw; the clock now falls back to `strftime`.
**Not drawn yet.** wsd's log (`WSD_CA_DEBUG=1`) shows our CA commits arriving every second (`scene 0 (client N): 3 layers, 0 images, 3 contexts`) but: (1) `0 images`: the `CGImage` contents of our layers are not decoded by `WindowServer/src/ca_scene.c` (the Dock's tiles are 128x128 Image objects with Texture records; ours are CA backing-store images of another kind: to inspect with `/tmp/ca-ool-*.bin` and `caparse.py`); (2) `context N bound to window 0`: `SLSSetWindowLayerContext(wid, ctx)` is not turned into a binding to our 31x30 windows, so the scene is painted on the full-screen window of the context at 0,0 instead of at 1063,0. Both are WindowServer / SkyLight work (ca_scene types and `wsd_layer_ctx_window`), not ControlCenter code. Next: decode our image kind, bind contexts to SLS windows, then the status items and the panel appear.

## Pixels on wsd (2026-11-18, later)
Two defects of `WindowServer/src/ca_scene.c` found with a host harness (compile ca_scene.c with a 20-line main that calls `ca_load_file` on a captured `ca.bin` + `ca-ool-*`; the capture comes from `/tmp` of the VM) and fixed: (1) the commit op 4 (`add_animation`: CoreAnimation sends one when a layer's `contents` change, the implicit action) was an unknown op, so **the rest of the message was dropped**, which included the layer carrying the image ("0 images"); it is now skipped up to the next layer record; (2) a later record that only changes the contents carries a zero geometry block and reset the layer to 0x0: geometry is kept when the new block has none. With both, ControlCenter's images are decoded (`3 layers, 8 images`) and **painted: the clock image appears on the wsd screen** (as boxes with "?": CoreText has no font files on the image, "System LastResort not available": the SF fonts must be taken from the Mac by `macdeps` like the cache).
Still wrong: **position**: the scene is painted into the full-screen window of its context at 0,0 (bottom-left in the screenshot) instead of at the SLS window (1136,0 144x30): `context N bound to window 0` in wsd's log, i.e. `SLSSetWindowLayerContext(wid, ctx)` does not bind the context to the window created by `SLSNewWindowWithOpaqueShapeAndContext` (type 5, the context object passed at creation). To do in `WindowServer` / `SkyLight` (`wsd_layer_ctx_window`, `sls_window.c`): bind at window creation too. Then fonts, then the panel.
Scripts: `iso-stack.sh` kills the image's own launchd (do not use twice); a variant that kills only ours (`pkill -f dnew/launchd/launchd`) and runs wsd from `/Users/alex/stk/wsd.new` was used for these runs.

## Position fixed (2026-11-18, same evening)
macOS 26's `SLSNewWindowWithOpaqueShapeAndContext` puts the CA context id into the **CreateWindow** request (field `ca_context_id`) and sends no `SetWindowLayerContext` for such windows (the trace shows no 30264): `do_create_window` now binds it (`wsd_bind_layer_ctx`). Also: the image row stride (`row bytes` 192 for 42 pixels) is honoured by the painter, and `GetAppearanceTheme` answers dark (before: light, so the glyphs were drawn black on the dark bar). Now the clock is on the wsd screen at 1136,0 (boxes: no fonts) and the three windows are at their places. Still missing: fonts (macdeps), the Control Center and Spotlight glyph images (only a thin column is visible: to investigate: vector fallback on pearOS, no CoreGlyphs catalogs there), then input (clicks) for the panel.
