# ControlCenter on pearOS

How `apps/controlcenter-cocoa` is installed and started on pearOS (the Mac frameworks it links come from the owner's Mac through `macdeps`; the binary and its sources are ours, BSD-2-Clause).

## Install layout
`/System/Library/CoreServices/ControlCenter.app` (our bundle: `Contents/MacOS/ControlCenter`, `Contents/Info.plist` with `com.apple.controlcenter`, `LSUIElement`). The Apple one is never installed on pearOS, so the path is free.

## Services (launchd job)
`pearos/com.apple.controlcenter.plist` declares the same MachServices as Apple's job (`com.apple.controlcenter.ccutil`, `.controlcentermodule`, `.show.toggles`, `.statusitems`, `com.apple.SystemBanner`, `com.apple.SystemBannerService`). The launchd of `d/darwin` takes at most 6 names per stub and 256 programs.

## Build
Today: a Mach-O built on the Mac VM (`research/cc-trace/deploy-ours.sh`, `make` here), copied to the image. Wanted: a build on FreeBSD with clang + ld64.lld and `-undefined dynamic_lookup` like `/open` (`open/build-appkit-bsd.sh`): needs headers for QuartzCore, CoreText, ImageIO, xpc, IOKit/ps, ApplicationServices that the open SDK tree (`dyld/tools/sdk`) does not have yet.

## Status of the run on the ISO test VM (2026-11-18)
Setup used (ISO test VM, `~/.pear/isotest`, ssh port 2224, cache disk on a virtio drive mounted at /System/Volumes): the thin Mac `dyld` installed at `/usr/lib/dyld` through a tmpfs + unionfs over `/usr/lib` (the ISO root is cd9660, read-only), `binmiscctl disable macho64 / machofat`, `kern.darwinator.{dyld=1,two_volumes=2,fast_sleep_ms=5}`, our `ControlCenter.app` built on the Mac VM copied to `~/cc` (chmod +x).
1. **Found and fixed (darwinator, `src/syscalls_event.c`): `getfsstat64` looped forever.** Two causes: the root of the ISO is cd9660, but the "second volume" logic only recognised ufs / zfs roots (count of the first pass one more than the entries of the second, so dyld never settled): now the root volume is the mount on `/`, whatever the file system; and the buffer of the second pass was `maxn-1` entries, which cut off the last real mounts when msdosfs mounts (EFI partition, cache disk) came before them: now there is room for them. The module was rebuilt on the lab VM from the releng/14.5 kernel sources and loaded in the ISO VM: the loop is gone.
2. **Next blocker:** `dyld: Library not loaded: /System/Library/Frameworks/Foundation.framework/Versions/C/Foundation ... (slice is not valid mach-o file)`. The ISO installs GNUstep stand-ins (ELF) at the Mac framework paths (`iso/manifest/frameworks.txt`), and the Mac dyld looks at that file instead of taking the library from the shared cache (the cache disk is there, `shared_region_check_np` is called). To do: make dyld take system libraries from the cache (the macOS 26 cache has them as "not expected on disk": check why dyld prefers the disk file, `kern.darwinator.use_cache`, the shared-region mapping of the cache from the disk's path), or keep the stand-ins out of the paths the cache provides when the Mac stack is used.
2b. **Found (same day): dyld looks for the cache in `/System/Library/dyld/` (and `/System/Cryptexes/OS/System/Library/dyld`), neither exists on the ISO** (the cache disk is at `/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld`, and darwinator does not redirect it). So the Mac dyld never saw the cache and went to the disk file (the GNUstep ELF). With a tmpfs + unionfs over `/System/Library` and a symlink `/System/Library/dyld -> /System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld` the "Library not loaded: Foundation" error is gone and the process runs on (it then waits: no launchd / window server in that VM). To do in the image: `/System/Library/dyld` (symlink, or a mount of the cache disk there) created by the overlay / rc script that sets up the Mac stack, instead of a manual unionfs. **Correction (later the same day):** the "spin" was not the app: the kernel stack of the process was `vn_fullpath_any -> vn_fullpath_dir -> vn_vptocnp -> _vn_lock_fallback`, i.e. `fsgetpath` (dyld asks for the path of a cache file) looping in the kernel on vnodes of my **unionfs** test mounts over `/usr/lib` and `/System/Library`; the process became unkillable (23 minutes of CPU, later runs queued behind it in state `DN` on the same vnode lock) and the VM had to be restarted. So: do NOT use unionfs for this; the image must provide `/usr/lib/dyld` and `/System/Library/dyld` in its own tree (the ISO build) or through nullfs/tmpfs copies. Earlier wording, superseded: the process RUNS (state RL, load 2.5 for 7 minutes, ignoring SIGTERM from `timeout`: it spins, probably in a kevent / workqueue loop while it waits for services that do not exist in that VM): to look at with `kern.darwinator.debug=2` and the real stack (launchd, WindowServer).
3. Then: services (launchd with the job plist here), WindowServer as SkyLight server, the CA render stub, as for the Dock/Finder (`d/session/pearos-desktop.sh`).

## Result of 2026-11-18 (evening): our ControlCenter RUNS on the ISO test VM
Clean setup (no unionfs): a tmpfs of 900 MB with copies of `/System/Library` (210 MB, plus a symlink `dyld -> /System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld`) and of `/usr/lib` (plus the Mac's thin `dyld`), each put over the original with **nullfs**; cache disk (virtio, msdosfs) on `/System/Volumes`; rebuilt `darwinator.ko` loaded; `kern.darwinator.{dyld=1,two_volumes=2,fast_sleep_ms=5}`; `binmiscctl disable macho64/machofat`. (The script of the run is in the notes of this session: tmpfs + `cp -a` + `mount -t nullfs`.)
Third darwinator defect found and fixed (`src/syscalls_more.c`): `fsgetpath` called `VFS_VGET` on the root mount with the file id of the caller; on the ISO the root is cd9660, whose VGET takes the number as a block offset and returns garbage vnodes, so `vn_fullpath` spun forever in the kernel (unkillable process, 23 minutes of CPU, procstat: `vn_fullpath_any -> vn_fullpath_dir -> vn_vptocnp`). It now answers ENOENT for a cd9660 root (a proper fix: look the mount up by the fsid the caller passes).
What happens now: dyld loads the app and Foundation, QuartzCore, CoreGraphics ... from the cache, `main` runs our code, `CCServices` creates the XPC connections, and the process waits in `mach_msg` (state `machmsg`) because this VM has no launchd stack; our log says `cc: window 0/1/2 not created` (no SkyLight server: the status-item windows need `WindowServer`). `kevent filter -17` is not implemented (logged 28 times, harmless so far).
Next: the services (the launchd of `d/darwin` with `com.apple.controlcenter.plist`, notifyd, cfprefsd, lsd ...), `WindowServer` + `wsbridge` as the SkyLight server, the CA render stub; then the status items and the panel should draw on WindowServer like the Dock does (`d/session/pearos-desktop.sh`).

## Stack on the ISO test VM (2026-11-18, later): the status items reach WindowServer
Built on the lab VM (`pkg install llvm21`, then `d/darwin/build.sh` and `make -C WindowServer SKYLIGHT=../SkyLight WindowServer`) and copied to the ISO VM (`iso-stack.sh`: WindowServer headless 1280x800 + our launchd with notifyd, wsbridge, the Mac's cfprefsd daemon/agent, lsd-stub, carender-stub, a svc-stub for `com.apple.PowerManagement.control`). With that stack ControlCenter stays alive and **WindowServer lists exactly the windows of the Mac**: `window 1 level 25 1063,0 31x30`, `window 4 level 25 1094,0 42x30`, `window 6 level 25 1136,0 144x30` (SkyLight window creation, levels and frames work through wsbridge). A crash was fixed on the way: `NSDateFormatter stringFromDate:` returns nil on pearOS (ICU data) and made `[NSAttributedString initWithString:nil]` throw; the clock now falls back to `strftime`.
**Not drawn yet.** WindowServer's log (`WSD_CA_DEBUG=1`) shows our CA commits arriving every second (`scene 0 (client N): 3 layers, 0 images, 3 contexts`) but: (1) `0 images`: the `CGImage` contents of our layers are not decoded by `WindowServer/src/ca_scene.c` (the Dock's tiles are 128x128 Image objects with Texture records; ours are CA backing-store images of another kind: to inspect with `/tmp/ca-ool-*.bin` and `caparse.py`); (2) `context N bound to window 0`: `SLSSetWindowLayerContext(wid, ctx)` is not turned into a binding to our 31x30 windows, so the scene is painted on the full-screen window of the context at 0,0 instead of at 1063,0. Both are WindowServer / SkyLight work (ca_scene types and `wsd_layer_ctx_window`), not ControlCenter code. Next: decode our image kind, bind contexts to SLS windows, then the status items and the panel appear.

## Pixels on WindowServer (2026-11-18, later)
Two defects of `WindowServer/src/ca_scene.c` found with a host harness (compile ca_scene.c with a 20-line main that calls `ca_load_file` on a captured `ca.bin` + `ca-ool-*`; the capture comes from `/tmp` of the VM) and fixed: (1) the commit op 4 (`add_animation`: CoreAnimation sends one when a layer's `contents` change, the implicit action) was an unknown op, so **the rest of the message was dropped**, which included the layer carrying the image ("0 images"); it is now skipped up to the next layer record; (2) a later record that only changes the contents carries a zero geometry block and reset the layer to 0x0: geometry is kept when the new block has none. With both, ControlCenter's images are decoded (`3 layers, 8 images`) and **painted: the clock image appears on the WindowServer screen** (as boxes with "?": CoreText has no font files on the image, "System LastResort not available": the SF fonts must be taken from the Mac by `macdeps` like the cache).
Still wrong: **position**: the scene is painted into the full-screen window of its context at 0,0 (bottom-left in the screenshot) instead of at the SLS window (1136,0 144x30): `context N bound to window 0` in WindowServer's log, i.e. `SLSSetWindowLayerContext(wid, ctx)` does not bind the context to the window created by `SLSNewWindowWithOpaqueShapeAndContext` (type 5, the context object passed at creation). To do in `WindowServer` / `SkyLight` (`wsd_layer_ctx_window`, `sls_window.c`): bind at window creation too. Then fonts, then the panel.
Scripts: `iso-stack.sh` kills the image's own launchd (do not use twice); a variant that kills only ours (`pkill -f dnew/launchd/launchd`) and runs WindowServer from `/Users/alex/stk/WindowServer.new` was used for these runs.

## Position fixed (2026-11-18, same evening)
macOS 26's `SLSNewWindowWithOpaqueShapeAndContext` puts the CA context id into the **CreateWindow** request (field `ca_context_id`) and sends no `SetWindowLayerContext` for such windows (the trace shows no 30264): `do_create_window` now binds it (`wsd_bind_layer_ctx`). Also: the image row stride (`row bytes` 192 for 42 pixels) is honoured by the painter, and `GetAppearanceTheme` answers dark (before: light, so the glyphs were drawn black on the dark bar). Now the clock is on the WindowServer screen at 1136,0 (boxes: no fonts) and the three windows are at their places. Still missing: fonts (macdeps), the Control Center and Spotlight glyph images (only a thin column is visible: to investigate: vector fallback on pearOS, no CoreGlyphs catalogs there), then input (clicks) for the panel.

## Does it work on WindowServer? (answer of 2026-11-18, late)
Partly. **Yes:** the three status-item windows exist at the Mac's positions, the clock (SF) and the Control Center glyph are painted by WindowServer, the theme is dark. **No:** (1) the panel window is created (`window level 22 800,0 656x964`, `CC_OPEN=1` opens it without a click) but **nothing is painted**: WindowServer's scene for the client keeps `3 layers, N images, 3 contexts`, the panel's context never appears, so its commit (one 656x964 image, 2.5 MB) does not reach `ca_scene`: it probably does not travel as a small out-of-line message like the 144x30 ones (a large commit, id 0x9c43, or a shared-memory Image through a port) and `carender-stub` / the decoder do not carry it: to capture and handle; (2) the Spotlight magnifier is not drawn, (3) no input: clicks cannot open the panel on pearOS yet, (4) the gallery is untested, (5) the setup is manual (nullfs copies, symlink, fonts, stack). Stale windows of killed instances stay in WindowServer's list (windows of a dead client are not removed).

## State of the panel on WindowServer (2026-11-18, night)
With the panel and gallery images cut into bands of 32 rows the panel DID reach the render server once (`34 layers, 187 images`) and was painted, but **shifted left by half its width** (about -328 px: layers anchored by their centre in `ca_scene.c`, ours positioned by `frame`), and in later runs its commit did not arrive at all (the window exists at level 0, no root for its context): the order of events at start (panel created before the run loop, `CC_OPEN=1`) is suspect. Open: (1) the half-width shift in `ca_scene.c` paint (anchor / position of children), (2) why the panel's context sometimes never commits, (3) the window level of the panel (22) shows as 0 in `wswins`. The server is now called `WindowServer` (socket `/tmp/WindowServer.sock`, CA socket `/tmp/WindowServer-ca.sock`, log `/tmp/WindowServer.log`); `iso-stack2.sh` follows the new names.

## RESOLVED (2026-11-18, night): the panel draws on WindowServer
Two causes, both in our code: (1) the panel (and gallery) windows were ordered with `DockWindow orderIn` (a transaction with level and order only): on pearOS the window stayed at level 0 and its commit was unreliable; now `CCShowWindow` does what the real ControlCenter does (window tags twice, level, order in one transaction): level 22 / 23 as on the Mac; (2) with `CC_OPEN` the panel was created before the run loop started: now 3 s after the start from the run loop. The "half-width shift" seen before disappeared with the unanchored band layers (no `anchorPoint` change: the children are positioned by their centre as `ca_scene.c` expects). Result on the ISO VM: the whole panel (tiles, glyphs, text in SF, sliders, Edit Controls) at 966,34 on the WindowServer screen, `34 layers, 33 images`. Still open on pearOS: clicks (events), the gallery and edit mode on WindowServer (not tested), the Wi-Fi / Bluetooth glyph differences (no CoreGlyphs catalogs: vector fallback), moving the manual setup into the ISO build.

## The panel on pearOS (2026-11-19): it draws, with all controls
Screenshot of WindowServer on the ISO test VM: `pearos/panel-on-pearos.png` (Wi-Fi / Bluetooth / AirDrop, Now Playing, Stage Manager, Screen Mirroring, Dark Mode, Screenshot, Focus, Display and Sound sliders, "Edit Controls"). Started by `pearos/iso-stack3.sh` after `iso-prep.sh` (the ISO is read-only/`snapshot`: a reboot loses the setup; ssh as `alex`, not root; the `d` daemons must be rebuilt with the current socket names: `sh d/darwin/build.sh` on the FreeBSD VM, an old `carender-stub` looks for `/tmp/wsd-ca.sock`).
What blocked it, found one by one: (1) `/tmp` is a 20 MB tmpfs and launchd's request log filled it (WindowServer: "listen: No space left"): log to /dev/null; (2) per-control layers made the panel's first paint ask CoreWLAN / IOBluetooth for the state of every control: with no daemon behind them the call never returns and holds dyld's lock (`procstat -kk`: the main thread in `ulock`): `CCStateText` and `CCSliderGet` answer from a cache refreshed on a background queue, `CC_NO_SYSTEM_SERVICES=1` does not load those frameworks (the FreeBSD bindings answer), and the tiles are drawn one per run-loop turn after the window is shown; (3) restarting only ControlCenter over a running stack hangs it (stale registrations in the launchd stub).
Not yet on pearOS: clicks / hover (the CGEvent tap has no events there), so the press and hover springs run only on the Mac; the Dark Mode disc shows no glyph; the AirDrop tile shows a Wi-Fi glyph.

## The whole desktop with the panel (2026-11-19, in progress)
The test stack above is minimal (headless WindowServer + stubs): no wallpaper, Dock or menu bar. The image's own desktop (Dock, Finder, SystemUIServer, Terminal, wallpaper, icons) runs on `wsd-fb` (the `fb` build of WindowServer) started by `/etc/rc.d/macdesktop`; to see the panel in it:
1. Boot the ISO (`snapshot=on`: every boot is clean), ssh as `alex`. Build `gmake SKYLIGHT=../SkyLight fb` of the current WindowServer on the FreeBSD VM; the image's `wsd-fb` is older (a panel on it is painted at 0,0 with stripes: the ca_scene fixes are missing). Put the new binary over `/usr/local/sbin` with a tmpfs copy + nullfs, `service macdesktop stop`, kill `wsd-fb`, `service macdesktop start` (run it with `daemon`: it closes the ssh session). **Do this before `iso-prep.sh`**: the prep replaces `/usr/lib/dyld` and disables binmisc, and the image's own programs (Dock...) then fail to start ("Exec format error"); with binmisc enabled our ControlCenter runs on the image's own runtime (machrun) and stops at `_bootstrap_look_up`.
2. `iso-prep.sh`, then the `d` daemons with `WS_SOCKET=/var/run/WindowServer.sock` and ControlCenter with `CC_LISTEN_ONLY=1 CC_NO_SYSTEM_SERVICES=1 CC_OPEN=1` (the geometry follows the screen width: `CCDX` = width - 1280, 640 on the 1920x1080 console; QEMU's `edid=on,xres=1280` was ignored by OVMF).
State: the desktop comes up on the new WindowServer and the panel window is created at 1440,0 (right place), but ControlCenter then waits in a Mach call (`machmsg`) and never shows it (level 0, no render context). It did draw completely on the minimal stack, so the difference is something the full desktop session changes (services of the image's own launchd, or requests that the bridge does not answer when the server has many clients). Next: log wsbridge's requests (the launchd stub's log goes to /dev/null because it fills /tmp) and see which request has no reply.
Input: WindowServer serves listen-only taps (`sls_tap.c`) and `wsbridge` has event channels, so `CC_LISTEN_ONLY=1` should deliver mouse events once the panel shows (`wsclick` / `wsmove` inject them); not verified.

## The panel on the whole desktop (2026-11-19): it works
`pearos/panel-on-pearos-desktop.png`: wallpaper, Dock, menu bar, desktop icons and Terminal of the image, and our Control Center at the right edge (every control; the panel is light because the server was started without `WSD_APPEARANCE=dark`; the clock and the icon of the menu bar are drawn twice, by SystemUIServer and by us, at the same place). The program is the one built ON FreeBSD (`build-bsd.sh`). What it took, in the order it was found:
1. the server of the image is the `fb` build of WindowServer; it must be the current one (older: the panel is painted at 0,0 with stripes) and started with `WSD_OPSET=26` (the SkyLight of the Mac cache is macOS 26.x; the server defaults to the table of 27, refuses the transactions with code 1001 and every window stays at level 0): `macdesktop_opset="26"` in `rc.conf` of the image (iso/overlay);
2. do the swap of the server BEFORE `iso-prep.sh` (it disables binmisc and replaces `/usr/lib/dyld`: the programs of the image, Dock...  no longer start);
3. `carender-stub` wrote every commit into `/tmp` (20 MB) and printed it: `CARENDER_TRACE=1` only; the log of the launchd stub must not go to a pipe (it blocks the whole chain) nor to `/tmp`;
4. the headers: CGFloat is a double and the prototypes say CGFloat (see Building on pearOS).
Still open: mouse events (the tap), the theme (`WSD_APPEARANCE`), replacing the status area of SystemUIServer, the setup in `iso/build.sh` (the program is built there, the cache is mounted by the user).
